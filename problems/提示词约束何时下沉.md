# 反复提醒 Agent 仍犯错，哪些约束该下沉到工具或框架？

[← 问题索引](README.md)

检索词：提示词太长、重复犯错、mock 还原、硬门禁、代理指标、框架、lint。

## 先看什么

先读 [R0011](../resources/R0011/README.md) 第一部分：自动还原取消一类错误；运行反馈应可核验；不准确的规则可能导致反向优化。

补充 [R0001](../resources/R0001/README.md)，铁律四与模式 6：能写成 Linter/CI 的规则不留在自然语言，`AGENTS.md` 每条规则对应一个真实失败，失败记录回灌成新规则；作者“可靠十倍”是强主张，未给误报与维护成本数据。

补充 [R0027](../resources/R0027/README.md)，第 5 步：一手说法把 harness 拆成两类——改 `AGENTS.md`（每条规则来自一次具体坏行为）与写程序化工具（截图、过滤测试）；作者同时声明“不知道业界有没有公认术语”，比二手转述克制得多。

补充 [R0030](../resources/R0030/README.md)，`Let it decide, enforce only what can't bend`：prompts、CLAUDE.md 与 skills 是请求，hooks、deny 规则与托管设置才是要求。给了两条判定：强调后仍不生效就改成 hook；hook 只是在表达偏好就删掉。

补充 [R0007](../resources/R0007/README.md) 的架构与静态检查层次，以及 [R0003](../resources/R0003/README.md) 的精简项目说明结构。

## 可以先试什么

以下为据材料归纳的待实践建议：选一类反复出现的错误，区分稳定行为约束与临时补丁，核实是否有准确、外部可取得的检测信号；先用实际例子测误报，再决定是工具、框架能力、阻断检查还是提醒。

## 还缺什么

没有用户项目误报、成本和可绕过性数据，不能仅凭反复犯错就增加硬门禁，更不必为每条提示词自建 runtime。

补充：[R0021：大仓 Harness 实战](../resources/R0021/README.md)，第 2.1、6 章补可判定规则下沉、软硬门禁与开发前后基线；原文阈值有差异，不能照抄为统一门禁。

补充：[R0022：Harness engineering](../resources/R0022/README.md)，定位 Enforcing architecture and taste，补自定义 lint、结构测试与带修复提示的错误；检查器正确性仍需验证。
