# 同时开很多 Agent 会话后，人忙于盯进度，怎样协调？

[← 问题索引](README.md) · [多 Agent 协作](../tags/多Agent协作.md)

检索词：多标签页、调度、派发、巡检、队列、共享记忆、管理者瓶颈。

## 先看什么

[R0013](../resources/R0013/README.md) 的五阶段演进与 `What you can do with this today`：先识别重复协调工作，固定重复流程可先建队列，不直接从多标签页跳到自治协调。

补充 [R0005](../resources/R0005/README.md) 的阶段证据、停止条件，以及 [R0012](../resources/R0012/README.md) 的权限、人工门和治理指标。

实现入口：[R0014：KiroCrew 仓库](../resources/R0014/README.md) 已记录固定 commit 的文档路径，可继续研究会话、记忆与调度；尚未审源码或实践，不能当作已验证解决方案。

## 观点差异与适用条件

- [R0013](../resources/R0013/README.md) 的软件工厂案例强调并行后需要分派、持久记忆和治理；[R0021 原文依据](../resources/R0021/README.md#关键摘要的原文依据) 7.4 则在四个串行调用点删除未带来收益的 Team Mode。一个处理实际并行，另一个消除串行流程的冗余机制，不能概括为所有团队都应增加或删除协调器。
- 本库判断：先确认任务能否独立执行、共享哪些可写状态以及由谁收口；只有确实存在协调成本时才选工具。仓库文档和案例自述不足以证明本项目会获益。

## 可以先试什么

以下为据材料归纳的待实践建议：记录一段时间中你花在拆解、派发、巡检、验收和排序的工作，找最重复的一项。先明确任务归属、输入输出与可审阅证据，再决定是否需要共享记录、队列或调度工具。

## 还缺什么

本库没有用户并行任务的耗时与质量记录。更多会话或更复杂管理者不自动提高收益；先验证协调成本有没有下降、质量有没有退步。

## 平台实现参考

[R0018：LoopForge](../resources/R0018/README.md)：对照角色、聊天工作空间、SOP 和审批入口，比较哪些协调动作可以固定下来；平台与 Local 范围不同，未实践验证。

补充：[R0021：大仓 Harness 实战](../resources/R0021/README.md)，第七章以串行任务为例删除无实际收益的 Team Mode，先检查复杂机制是否只在修复自身副作用，不推广为全面反对并行。

## 缺失证据与待验证

需要用户任务的依赖图、冲突与等待记录、人工协调耗时，以及并行前后的交付质量和总成本；缺这些记录，无法判断多开会话是否值得，也不能从合并 PR 数量推导效率提升。

## 补充参考：任务归属与人工注意力

[R0026：dsh-superagent-prototype](../resources/R0026/README.md) 的 001、003—005 文档描述主会话只路由，各 Ticket 独立执行，范围内追问由 Executor 负责，超范围再交回；面板先显示待人决定、审查或排障事项。可与 R0013 的大规模协调演进、R0021 的串行简化对照。它面向一个仓库，不是已核验的跨仓库万能调度器；独立目录不保证进程、凭据或文件权限隔离，缺并发与实际人工耗时数据。
