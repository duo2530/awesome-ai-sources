# 自检怎样保持独立视角，并检查当前 diff 以外的影响？

[← 问题索引](README.md)

检索词：代码审查、独立会话、关联应用、外部接口、SRE、check reports。

## 先看什么

[R0009](../resources/R0009/README.md)，定位 `独立会话、独立视角` 和 `研发自检的三大挑战`：由新会话、独立工作区读取变更、需求、规则和相关依赖，分主链路与模块检查，按角色产出证据。

补充 [R0008](../resources/R0008/README.md) 的真实环境验收与 [R0005](../resources/R0005/README.md) 的前后对照证据。

补充：[R0011](../resources/R0011/README.md)：补充常驻 reviewer 的偏向、平台独立重跑与验证信号自身的校验。

补充：[R0012](../resources/R0012/README.md)：明确区分任务内持续反馈和独立最终检查，PR 审查不替代人的意图与风险判断。

## 可以先试什么

以下为据材料归纳的待实践建议：先选一个变更，整理给检查者的规格、diff、规则和关联依赖，要求问题指向证据；涉及未覆盖系统时明确限制，不仅写“通过”。

## 还缺什么

独立会话不能自动保证发现所有问题；本库没有用户项目的跨应用依赖图与自检效果测量。

## 安全审计参考

[R0017：Cloudflare security-audit-skill](../resources/R0017/README.md) 将发现者、候选验证者和最终记录检查者分开，并用台账记录未覆盖范围。详见[怎样减少 AI 安全审计误报？](AI安全审计如何减少误报.md)。未执行该流程，不把其证据标准视为一般功能自检的完整替代。

## 实现参考：独立评审作为合并门禁

[R0029：orbi](../resources/R0029/README.md) 把 PR 交给一个独立评审会话，评审在同一会话内修复问题，只有 reviewed head 能合并；不可恢复失败标 `ai-blocked` 交人。这是项目自述的机制，本库未核验其是否由平台分支保护真正强制，也未检查绕过路径。

补充：[R0030：Your coding agents made you a manager](../resources/R0030/README.md) 的 `/code-review` 把 diff 交给没看过对话的新 subagent，并可以限定只找正确性问题、忽略风格；作者把“测试绿就批准大 diff”称为 code ratification，不算审查。

补充：[R0031](../resources/R0031/README.md)：六层检查按风险分层，人工审批只留给高风险与敏感路径；bot 批准不能顶替人工批准，新 commit 会撤销旧批准。
