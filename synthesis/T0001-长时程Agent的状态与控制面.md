# 长时程 Agent 的状态放哪里：LoopX 与 Orbi 两条路线

- 综合编号：T0001
- 主题：长时程 Agent 的状态与控制面
- 涉及资料：[R0028：loopx](../resources/R0028/README.md) · [R0029：orbi](../resources/R0029/README.md)
- 最近修订：2026-11-15
- 依据范围：两篇条目的“一眼了解”“关键结论的依据”“适用条件与限制”四节及其 README 阅读记录；两篇均只读 README 与仓库元数据，未读 docs、源码、测试与基准数据
- 内容处理：已有 AI 综合；未经用户实践

## 当前认识

1. **两条路线的分水岭不是“自动化程度”，而是状态存在哪里。** LoopX 把工作状态从宿主抽到独立控制面（本地 SQLite、团队 PostgreSQL）；Orbi 直接把 GitHub Issue 当唯一状态存储，没有数据库、队列或常驻守护进程。性质：本库归纳，依据 [R0028](../resources/R0028/README.md) 的“一眼了解”与 [R0029](../resources/R0029/README.md) 的 Why Orbi 节。
2. **两者都主动排除“自主生产控制器”，把人批准不可逆动作写进设计。** LoopX 声明危险权限、发布、生产写入与最终归属仍归人；Orbi 声明 AI 从不合并、不推送受保护分支，不可恢复错误打 `ai-blocked` 交给人的。性质：项目文档自述，不是本库验证过的强制边界。
3. **验证机制是两套不同答案。** Orbi 用“独立评审会话 + 只有 reviewed head 才能合并”的合并门禁；LoopX 用配额判定回答“该干、该问、该等还是该停”，并保存证据与租约。性质：项目文档自述，实现均未读。
4. **两边的效果证据都很弱，且弱的方式不同。** LoopX 的 LHTB 均分 +17.3% 是作者自测，README 自己写明单次试验、预算不等、不是因果估计；Orbi 用自家仓库的 issue → PR → release 循环和录屏做证明，属 dogfooding，没有第三方评估或失败率。性质：项目自测与自述；本库均未复现。

## 对照

| 维度 | LoopX（R0028） | Orbi（R0029） |
|---|---|---|
| 定位 | 与宿主无关的控制面，宿主负责跑模型与工具 | 以 GitHub Issue 驱动的自动交付系统 |
| 状态存储 | 自有存储：本地 SQLite，团队 PostgreSQL | GitHub Issue 本身，无数据库与队列 |
| 谁执行代码 | 宿主（Codex、Claude Code、DeepSeek Harness 等） | Pi 编码 Agent，每 5 分钟由 tick 触发 |
| 触发方式 | 配额判定“该继续、该问、该等、该停” | Issue 打上 `ai-ready` 标签 |
| 验证与合并 | 保存证据、租约与恢复记录；规则在文档 | 独立评审会话审查，只有 reviewed head 可合并 |
| 失败处理 | 恢复记录与租约；人工门分开 | 可恢复回原 PR 修，不可恢复标 `ai-blocked` 交人 |
| 人工门位置 | owner、安全、发布、私有数据分成不同的门 | AI 不合并、不推保护分支；发布由人触发 |
| 部署形态 | `pip install loopx`，含桌面端与插件包 | systemd（Linux）/ launchd（macOS）定时器 |
| 许可 | Apache-2.0（v0.4.8 起，更早 MIT） | AGPL-3.0 或 Sustainable Use License v1.0 |
| 证据来源 | README 自测 benchmark，作者自认非因果 | 自家 dogfooding 循环与录屏 |

表中每一行的依据都来自对应条目已读的 README；未读 docs 与源码，不据此判断实现是否与文档一致。

## 共同点与真实分歧

共同点：都把“人批准不可逆动作”当作前提而不是失败兜底；都用可检查的契约（配额、标签、评审会话、分支保护）替代提示词自觉；都明确反对把“有 Agent 在跑”当成“有进展”。

真实分歧只有一个，但很硬：**状态由谁托管。** 把状态放在 GitHub 上，等于把并发、锁、权限和审计交给现有平台，换来零额外基础设施；把状态抽到控制面，换来跨宿主、跨仓库和可迁移，代价是自己维护一致性、恢复与配额语义。这个选择决定出问题时你排查的是 GitHub 还是自己的状态层。

## 证据缺口

- 双方 docs 与源码均未读：Orbi 的“只有 reviewed head 能合并”是否由仓库分支保护强制、能否绕过，LoopX 的 gate 是否可被宿主侧绕过，都没有核验。
- 没有任何失败率、回滚率、人工介入次数或维护成本数据；Orbi 的自家循环与 LoopX 的自测都不能替代。
- LoopX 的 `benchmark/LHTB` 方法未读，无法判断任务选择与评分口径是否合理；Orbi 的“不可恢复”判定规则未读。
- 两篇都是单作者/小组 README 视角，未读 issue 历史，不能判断长期维护状况。
- 本库没有在用户项目中运行任一方，也没有做单仓多 Agent 并发实测。

## 修订触发

- 读到任一方 `docs/` 或源码中与授权、合并门禁、恢复相关的实现时，回来改写第 2、3 条与对照表。
- 收录第三条同类资料（例如以 PR 队列为中心或自建状态机的方案）时，重排对照维度，不把两方框架硬套上去。
- 任一方发布新版本并改变门禁或状态模型时，保留本次读到的固定 commit 作为旧依据。
