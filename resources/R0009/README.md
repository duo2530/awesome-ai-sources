## 一句话说明

把代码生成扩展为有标准产物、阶段质检、独立评审与统计反馈的需求交付体系，同时按工作复杂度和新旧代码范围调整流程。

## AI 摘要与要点

作者认为，仅提升代码生成速度会把瓶颈转移到质量检查、信息衔接和人工编排。其 2.0 方案把自动化生产与规范建设分轨推进，先维持现有链路，再逐步切换升级后的规范。

| 组成 | 解决什么问题 | 文中的做法 |
|---|---|---|
| Harness 约束 | 按什么标准工作 | 原则、宪法、规则、正反判例分层；应用说明标注新规区、过渡区和旧规区 |
| Spec 过程 | 怎样分阶段产出 | spec → plan → 分批 tasks → 执行 → 检查，保留过程材料、决策与会话日志 |
| 独立自检 | 谁判断做得对不对 | 新会话与独立工作区，读取 diff、规格、规则和相关依赖，从产品、研发、安全/SRE等视角出具报告 |
| 统计与 Loop | 怎样发现反复问题 | 检查阶段材料与 session，提出规范改进，再用后续需求观察效果 |
| 执行环境 | 怎样支持本地迭代和组织审计 | 本地调试、平台正式执行；云端分身产出待交付成果，最终交付仍有人工 review |

值得保留的取舍：

- **不把所有任务都重管**：按需求复杂度分级；单应用不机械套用跨应用的项目级结构。
- **不顺手改造老代码**：先识别规则适用范围，未规整区域与灰色地带需补充研究或人工决定。
- **控制单批工作复杂度**：让 tasks 细化 plan，避免一次跨越过多内容导致上下文丢失。
- **把检查看作独立接口**：编码与检查通过标准产物沟通，检查需覆盖关联应用和外部影响，不仅看当前 diff。
- **区分改进建议与统计指标**：文中“Agent 生成需求”按 ID 和指定产物校验计数，不等于质量或业务收益已证明。

文中提出的领域知识库、数字员工独立身份等仍有筹划或长期方向；不能把整篇架构图都视为已完成部署。
