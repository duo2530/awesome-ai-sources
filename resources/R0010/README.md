## 一句话说明

针对三套前端框架与两种数据库的组合，先写用户旅程验收标准，完成界面后做浏览器预演，再编写可复用的 Playwright E2E 回归测试。

## AI 摘要与要点

作者以 TinyShip 的多框架、多数据库 monorepo 为例，介绍 `Spec → Code → Verify → Test → Green` 五阶段流程：

| 阶段 | 文中做法 |
|---|---|
| Spec | 在测试目录的 TEST-CATALOG 中写清用户操作与预期结果，先明确关键用户旅程 |
| Code | 实现功能，将共用逻辑放在共享库，保持不同应用的一致性 |
| Verify | 先用浏览器自动化走真实流程，检查交互问题与元素定位 |
| Test | UI 成型后再写 Playwright E2E，用已观察到的界面确定选择器 |
| Green | 检查三个框架与两种数据库的组合；按变更场景选择相关或全量回归 |

核心区别是“验收标准先写，依赖 UI 的测试代码后写”。作者没有因此否定所有测试先行方式，而是在这个项目中区分自然语言验收设计与具体浏览器脚本。

执行取舍：新功能后跑相关 spec，发版与大重构时跑全量；作者将 E2E 放在本地，CI 只跑类型检查与构建，理由是运行时间和环境依赖。这是作者当前项目的选择，不是所有项目的统一建议。

## 适用边界

- “两天完成”“核心流程 100% 覆盖”和节省 token 的数字属于作者陈述，本轮未独立测量；用例覆盖不等于发现所有缺陷。
- 文中关于 agent-browser 实现、性能与 token 节省的说法未重新核验；本轮没有安装、启动浏览器或执行测试。
- 后写依赖 DOM 的 E2E 脚本是该项目经验，不能扩写为所有浏览器测试都无法测试先行。
- 本地跑 E2E、CI 仅类型与构建是具体成本和环境取舍；不意味着其他项目应取消 CI 回归。
- Green 段要求六种组合，后文简述全量运行时主要写三个 app，实际采用时仍需明确数据库矩阵与运行记录，不能把文字流程当作六组已通过的证据。
- 原文未提供作者署名与测试报告，作者身份、实际稳定性及回归有效性仍未独立确认。
