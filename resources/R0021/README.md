## 一句话说明

在跨子仓库的业务大仓中，用角色契约、阶段产物、可执行门禁、人工确认和项目索引，把 AI 写代码连接到可审阅的团队交付。

## AI 摘要与要点

文章基于 TAB 平台实践，关注需求不完整、方案与实现失配、验证缺失和交付动作遗漏。先约定全链路 SPEC，再拆认知职责，将可判定动作下沉成脚本，根据真实失败调整阶段与协作机制。

| 关注点 | 作者实践 | 可借鉴的判断 |
|---|---|---|
| 六类资产 | Rule、Skill、Sub Agent、Workflow、Scripts、MCP | 分别组织约束、方法、认知、路由、检查与外部接口 |
| 角色边界 | 需求、方案、开发、审查四角色，加外层总控；下游不得直接改上游产物 | 验收和设计的修订应回到有责任的环节 |
| 阶段拆分 | 13 个条件化阶段，根据独立失败模式与回退位置拆分 | 阶段数是项目选择，不是通用模板 |
| 检查顺序 | 真实 HTTP 集成测试前置到代码审查；开发同时交付测试手段 | 先暴露便宜且明确的失败，减少昂贵的重复审查 |
| 门禁与基线 | 七道检查区分硬阻断和软警告，比较开发前后的失败集合 | 不依赖“历史问题”的口头解释，软失败也保留证据 |
| 人工关卡 | 需求确认、条件化方案确认、异常熔断，减少反复文件审批 | 自动执行与关键业务决定分开 |
| 协作简化 | 串行场景未用到 Team Mode 独有能力，删除消息和生命周期协议 | 先核对复杂机制有没有实际收益 |
| 项目知识 | 改动者维护代码地图，总控维护任务看板 | 团队共识在可审计仓库中对齐，个人偏好另存 |
| 外部交付 | MCP 方法限定语义、触发阶段、幂等和审计，失败记录并降级 | 先让开发验证稳定，再扩大外部副作用范围 |

优先读第六章的门禁与基线、第七章的 Team Mode 卡死复盘，再读第四、八、九章的产物所有权、共享知识与外部写操作。

## 适用边界与查漏补缺

- 项目规模、50+ 需求、30—75 分钟、约 70% 集成一次通过率等是作者自述，本轮没有原始日志或独立复测。
- “模型没有否决欲望”“半自动是唯一稳定形态”等是作者判断，不能推广为所有模型与团队的结论。
- 第 2.4、3.1 对 bugfix 复现概括较强，第 3.3 则明确仅 bugfix 且用户要求时触发；采用时需核对实际条件。
- 各章节覆盖率例值不同（分层阈值、80% 与门禁增量 85% 等），不能合成单一通用阈值，覆盖率也不独立证明断言有效。
- 第 6.2 区分软失败不阻断，第 6.3 又概括只有新增失败阻断。实际实现需明确门禁类型与基线规则优先级；旧失败不因此变得无风险。
- 未提供完整脚本、基线防篡改与失败匹配实现；需进一步验证代码版本、环境差异、证据归属和可绕过性。
- MCP 语义封装不等于权限隔离已强制落实；所有 MCP 失败软降级是作者取舍，应分别报告代码验证与外部交付，不能把 MR 或归档写入失败包装成完整交付。
- 任务看板并发更新、冲突处理、上游修订导致下游失效、取消与恢复规则仍缺实现证据。
- 删除 Team Mode、自动接受文件编辑都是特定宿主与权限场景的修复，不代表所有项目应禁用团队机制或放宽权限。
- 未执行原文命令、部署沙箱、调用 MCP、提交 MR 或发送通知。

补充：[R0022：OpenAI Harness engineering](../R0022/README.md) 以新建内部产品为背景，描述较少阻塞门禁和更多 Agent 间审查；与本文半自动关卡是不同取舍，不合并为唯一模式。
