## 一句话说明

用可审阅、可版本化的产物串联计划、设计、构建、测试、部署和维护，让自动触发、执行反馈与治理边界共同推进交付，人保留目标与风险判断。

## AI 摘要与要点

文章认为，代码生成加速后，瓶颈转向计划、检查、交接和部署审批。因此需要保留原有责任与控制目标，重新安排执行与证据，而不是只把 AI 放进编码环节。

| 阶段 | 关键变化与交接物 |
|---|---|
| Plan | 从提出者的意图生成 `intent.md`，说明问题、结果、约束与待确认项，经产品负责人纠正与接受 |
| Design | 将意图转成 `spec.md`，应用组织政策，先解决或升级冲突，再由人决定是否推进 |
| Build | 根据规格生成可审阅的 `plan.md`；项目说明、skills、工具及构建期检查共同提供工作条件 |
| Test | 持续运行代码验证，并回归测试模型、提示词、skills、hooks 等配置变化；区分任务内反馈循环与独立最终检查 |
| Deploy | 按严重程度组织 PR 审查，结合分支保护、权限、沙箱和环境分级，保留生产授权与可演练回滚 |
| Maintain | 用确定性监测触发诊断，发现写回新的意图或经审查的修复，生产事件再补入评测与回归 |

贯穿全篇的实践原则：

- **先手动跑通，再连接触发器**：阶段接受的产物成为下阶段输入，不必同时改造全部阶段。
- **每类产物确定权威来源**：Git 可以是权威记录，也可以是既有系统的工作副本；最低限度需要可追溯的双向关联。
- **区分建议与强制机制**：项目说明和技能承载知识，必须坚持的限制需要其他执行层支持；配置存在不等于机制已验证有效。
- **并行受审阅容量约束**：独立任务隔离执行，重复验证可封装为子任务；不能仅用产出或会话数量衡量成功。
- **每项实践同时观察过程与结果**：如响应或审查耗时，还应结合返工、变更失败、线上遗漏和重复事件观察。

本文属于厂商实践指南。表中的文件名、候选规模和组织方式是方案例子，并非本库或所有团队必须照搬的标准。

## 适用边界

- 作者与首次发布日期来自剪藏元数据，尚未远程核验；剪藏创建日期不等于文章发布日期，也未记录原文更新时间。
- 文中包含厂商产品、版本、beta 状态、计费与配置字段的具体描述，本轮仅整理提供的文本，未确认其当前可用性；不能直接拿示例部署生产。
- 示例用命令字符串及环境变量表达授权意图，不能仅凭示例就认定能覆盖所有执行路径或证明真实审批；需实际验证机制与证据。
- 监测中的 1/2/3σ 和滚动基线是文章示例，不是通用异常检测阈值；是否适用需结合具体数据和误报成本。
- 文中“可证明修复”的说法依赖事先固定且有效的测试；不能由测试通过推断需求完整、未覆盖分支安全或所有缺陷消失。
- 原文“约束后任意会话都遵守”等强保证需要实际环境验证；本库没有把建议性文档或独立审查当成绝对防绕过证明。
- 六阶段是组织材料的方式，采用顺序由先决条件与瓶颈决定；不必为每个小任务建立全部产物、自动化与审批。
- 本轮没有运行原文命令、安装 skills、启动子 Agent、接入服务或配置监控、扫描与部署。
