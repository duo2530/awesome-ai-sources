## 一句话说明

以阶段上下文、工具编排、人工确认门和验收证据串起业务需求交付，并在结项时区分稳定知识、流程改进候选与仅需归档的材料。

## AI 摘要与要点

作者把主要瓶颈定位在代码之外的串联成本：人不断切换平台、补上下文、判断下一步和回收经验。方案按上下文输入、业务专家编排、工具执行、反馈学习四层组织，以当前需求材料和长期知识启动，再逐阶段生成可审阅的过程产物。

| 阶段 | 主要产物与推进条件 |
|---|---|
| 需求进入 | 拉取需求材料和长期业务知识，形成初始上下文；事实缺失或冲突时补充 |
| 需求澄清 | 生成目标、非目标、验收标准和待确认问题，形成 requirements；经人确认再推进 |
| 技术方案 | 在 plan 中明确影响范围、配置、测试、真实环境验证及回滚；确认后再编码 |
| 实现与评审 | 依据业务行为先写测试，再实现；建立变更与测试锚点映射，结合静态检查与内部 review |
| 验收与发布 | 独立环境验证正例、反例与回归，保存接口、日志、指标等证据；主预发及线上发布仍需人工确认 |
| 观察与结项 | 发布后回读运行证据；回看评论、修正与验收记录，生成知识和流程改进候选 |

结项材料分三类处理：稳定业务知识经审阅后进入长期 wiki / codemap；反复出现的问题形成 skill / prompt 改进候选；一次性调试和实现细节只留归档。过程材料不会直接升级为长期事实。

作者采用代码仓库、项目记忆仓库和长期 wiki 仓库分层，并使用 Multica、内部平台 CLI / API 完成串联。这是该案例的实现方式，不意味着其他项目必须使用相同产品或三个独立仓库。

## 适用边界

- 作者说明是个人实践与观点；“真实业务已跑通”属于作者陈述，本轮未独立验证交付效果。
- 当前主要为单 Agent 后端流程；前后端、测试及 PD Agent 的团队协作是后续规划，不能写成已全部落地。
- 文章明确承认缺少系统化效果度量；人工介入次数、返工率、验收通过率和线上问题等是待建立的衡量维度，不是已经改善的测量结果。
- 文中用本地 pre-push hook 实现检查，但未展示所有入口或服务端的防绕过保证；不把“绕不过去”扩写为所有环境都不可跳过。
- 过程产物与长期知识需选择性审阅；不能把自动汇总、一次任务推断和稳定业务事实混为一谈。
- 内部平台、鉴权与运行时存在接入成本。本文命令、部署、发布和外部通知只是参考材料，本轮没有执行。
