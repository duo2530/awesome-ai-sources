> 这是 Lauren Tan（poteto）在 AI Engineer 大会上的演讲，介绍她所在 Grok Bot 团队如何通过软件工程基础设施——可强制执行的架构与 lint 规则、运行时验证、以及 TLA+ / Lean 形式化验证——让 AI 编码代理产出可信代码，从而实现单月 11000 个 PR、回滚率约 0.5%。适合正在搭建 AI 编码代理工作流、关心代码质量与自动化审查的工程师。

## 把垃圾代码变成黄金

好，再说一次，我叫 poteto。我在 SpaceXAI 做 Grok Bot。先请大家举个手。有多少人看过别人写的代码，然后心里想：这全是垃圾代码？我也是，但今天我想说服你，你能把这种垃圾代码变成黄金。

上个月我干了件疯狂的事：我往生产环境发了 3000 个 PR。在有 agent 之前，我们其实从不关心产出量，除了那些极端的个例。在我上一家公司，我们管这种人叫编码机器。比如 Bret Taylor，他很有名的一件事是用一个周末重写了整个 Google Maps，就是那种效率高得离谱的工程师。而有了 agent，现在任何人都能成为编码机器。

我的观点是：软件工程师的工作、作为软件工程师的元问题，就是想清楚怎么在把生产力大幅提上去的同时，保持甚至提升代码质量。有人喜欢把这叫软件工厂，但我喜欢简单点。我觉得核心就是信任——不是盲目信任，而是投资在 agent 的环境上，这样你才能相信 agent 会做正确的事。要达到那一步，需要花不少功夫。我花了六个月，才做到能发出几千个 PR，而且是很多个 PR 在睡梦中就发出去了。但这肯定是可行的，而且你会比我快得多。

## 把时间投在确定性约束

那我们先聊聊，怎么从一个低信任的环境走到高信任的环境。这个倒金字塔就是我对「该把时间花在 agent 环境哪一层」的看法。最上面两层是确定性的，也就是用代码本身：良好的 API 设计、架构、重构，或者用 lint 规则、类型系统、编译器，还有各种测试。你可以把这两层结合起来，约束 agent 能做什么，并默认逼它们做正确的事。

验证，包括运行时验证和形式化验证，是很好的叠加手段，用来发现 bug，检查你系统里希望成立的性质和不变量，也能帮你确认 agent 是否理解了你的目标和意图。最后，你还要在上面加一点点文字层面的东西。比如规则、技能、AGENTS.md，这些都需要人来判断。

## 代码库是智能体的花园

不过我们先从代码库说起。Agent 的输出取决于它的输入。所以输入的质量真的至关重要。而恰好，你的代码库就是其中最大的输入之一。所以每次你在纠正 agent 的时候，想一想怎么把它变成一个确定性的检查，而不是往你的规则或 AGENTS.md 里再加一行。因为写在代码里可复现性高得多，也让你更敢信任它。

我喜欢用的一个类比是，你的代码库就像一座花园。以前代码是一次几个 PR 地到来。我记得 2024 年去上班，审阅同事们写的 3 个 PR。而今天这个数字更像是 300。所以现在每个工程师其实都是一支由几百甚至几千个 agent 组成的团队。代码到来的速度太快，几乎像一条连续的流，甚至感觉是有机的，像一个活物。

在这个类比里，你的代码库、你施加的约束、你立起的护栏，就是那些坚实的地基，agent 新写的代码就绕着它们生长，就像这张图里的建筑一样。所以在很多方面，软件工程师这份工作正在变得像园艺，因为代码是 agent 最大的输入。这意味着任何变通做法、反模式、废弃代码、技术债，现在都很可能被下一个 agent 原样抄走，因为它在你的代码库里看起来就是既定模式。就像你的花园里长了些杂草或害虫，转眼之间就蔓延得到处都是。所以你要尽量让代码库保持干净，这样 agent 抄到的永远是好的东西。

## 用约束消灭坏模式

好，我们来看一些真实的例子。Dune 是我们为 Grok Bot 打造的客户端框架，就是为了实现这种有机架构的想法。从技术上讲，它其实没那么有意思。你可以把 Dune 大致看成 Electron 应用的 Next.js。但 Dune 有意思的地方在于，它有很多约束和 lint 规则，我们把构建桌面应用时学到的很多经验都固化进了这些约束和规则里。

其中一个经验是：任何需要细致拿捏才能用好的东西，往往都会带来垃圾代码。你知道，经典例子就是 React 里的 useEffect。它有它的用武之地，但经常被误用。有人开玩笑说，用 useEffect 得有个博士学位。换句话说，它确实需要很多细腻的把握才能用好，而 agent 并不擅长用它。

所以我们的做法就是直接在产品代码里禁用它，只在 Dune API 内部的少数位置允许使用。实际上，这个问题现在已经被彻底消除了，我们再也不用在代码审查时抓这个问题了。

我们使用的另一个有意思的模式是通过目录结构来提供上下文。我们在 Cursor 上看到的一个反模式是，agent 经常会把主线程代码导入到渲染线程，从而导致长任务和卡顿。所以在 Grok Bot 和 Dune 应用里，我们把这一点变得非常非常常规化。我们有两个顶层目录，字面就叫 Electron render 和 Electron main，而它们之间的导入会被我们的依赖图分析器和一些 lint 规则禁止或拦截。再说一次，这些 lint 规则设置起来很简单，但这意味着代码审查时我们少了一件需要审查和思考的事。

## 每次纠正都变成检查

还有一个让我意外的现象是，agent 会使用 Markdown。比如文档、代码注释、规则或技能，它们会把这里当成一个地方，写下自己不做正确之事的理由。或者，不知道你有没有见过这种情况：它们会对你做的一个小修正过度反应。然后把它当成永远不能再打破的硬性规则。这是 Cursor 上的另一个例子。

所以智能体特别喜欢用命令式定时器。比如 setTimeout、requestAnimationFrame、requestIdleCallback，它们把这些当作快速修复手段，其实只是在给 VS Code 的命令式风格和 React 的声明式风格之间的架构冲突打补丁。也就是说，我们选择的架构反而让客户端和智能体的表现都变得更差了。如果你在 JavaScript 里做过性能优化，你就知道：当大量定时器被快速创建和销毁时，会引发大量的主垃圾回收，从而导致严重的延迟和卡顿。但最糟的是，智能体还写了一堆代码注释——就像这里红色标出的那样——来解释这个快速修复为什么是合理的。不知不觉间，定时器就蔓延到了各处，应用的性能也实实在在地受了影响。

在 Grok Bot 里我们吸取了教训，决定直接禁掉 99% 的注释，因为它们太容易过期失效。反正人类也根本懒得去读那些注释垃圾。而且它还给智能体留了一个逃生舱口，让它有借口因为事情难做就不去做正确的事。注释最糟糕的地方在于，它们是没法强制执行的。所以那些初衷很好的东西——比如「我要告诉下一个智能体不要做某件事」——到头来根本不是你能信赖的东西。所以在 Grok Bot 和 Dune 里，我们现在有了 lint 规则，能给出友好又很有帮助的错误信息，告诉智能体去修复根因、修复真正的问题，而不是只在表面打补丁。

我们的总体原则是：每一次纠正智能体，都要把它变成一条确定性的检查；或者去想怎么通过更好的 API 设计、更好的架构，把这个问题从代码里彻底消除掉。如果你这样做得足够多，你会发现代码审查时要盯的东西越来越少。到某个时候你会意识到已经没什么可审的了，可以直接让智能体合并掉它们自己的大部分 PR。

## 验证让智能体更自主

好，继续。验证也是让智能体更自主、同时提升我们对其工作的信心与信任的关键一环。我们的代码审查流程现在实际上已经收缩为看验证产物了。比如视频、截图、图表、形式化验证。最基础的例子是运行时验证，说白了就是给你的智能体一个自己运行代码的方式，并让它使用你们人类开发者同样在用的调试工具，比如 Chrome DevTools Protocol。

在我们的运行时验证技能里，有个东西我们叫它功能地图。它基本上就是一张站点地图，只不过列的是从用户视角看你的应用里所有可用的功能。有了这个，当你说「左边侧边栏那个玩意儿」时，代理就不用猜了，它给了大家一套共享词汇。我们还在这些技能里用上了自定义 CLI，这样代理每次都能复用同一个 CLI 和驱动，减少了 token 消耗。而且它是可测试的。

最近我们还开始研究形式化验证。我们现在用 TLA+ 对主要用户流程做模型检查，比如跨多设备、多平台的通知。我们也用 Lean 来证明某些算法。比如我们自己写了一个自定义虚拟化库，我们用 Lean 来检查它没有闪烁或抖动的问题，这个方向我们还在试验。总体来看非常有前景。

我们已经通过形式化验证发现了不少 bug，但它显然不是银弹。我们把它当作又一个工具，代理环境里的又一层。

这段视频很快。另一件我们刚开始研究的事，是给我们的 UI 做基于属性的测试。我们用了一个叫 Bombadil 的库，它也已经抓到了一些 UI bug。

好。往大了看，我看到 Cindy 的一条推文，六个月前她说她没法信任自己的代理，因为总有一些隐蔽的 bug 被合进去。对她来说，真正缺的、让她没法信任代理的，是验证流程。六个月后的现在，她说她每天 70% 的 token 都花在验证上。我觉得这和我看到的情况一致，我的大部分 token 用量也都花在验证上。

如果你仔细看我们的流程，这里没有任何一样是全新的、我们从未有过的技术。它们都只是好的软件工程工具，只不过以前用起来的成本可能高得离谱，因为难理解、难维护。但 Agent 把这项成本大幅削减了。说真的，我们正在进入软件测试与验证的黄金时代，因为 Agent 让我们能把一切测到远超以往经济可行程度的水平。而形式化验证还能帮你更好地推理产品应该如何工作，以及你的 Agent 是否真的理解你的意图和目标。

我在自己的 pstack 插件里做了个叫 state chart 的新技能，它可以帮你从用户视角把状态机可视化出来。我发现把它和我们提供的视频、截图放在一起看，审阅起来容易多了。所以这个一直很好用。

## 高速交付也能保持质量

抱歉，刚才有点闪。好。现在来看看「应许之地」是什么样子。投入了这么多，你能得到什么回报？

在 Grok Bot 团队，我们的速度正在起飞，而且还在快速攀升。上个月，我们团队向生产环境提交了惊人的 11000 个 PR，这个数字太疯狂了。我们发布客户端的节奏也加快了。我们大约每天都会切出一个新的稳定版本。核心团队的产出也多了很多。

我们还多了很多随手的、路过的贡献者，他们手里未必有多少上下文。但他们也在贡献。10 月，大约有 227 人至少贡献了一个 PR。

所以尽管速度在加快，你可能会想：这不是要乱套了吗？这不是要变成一堆垃圾代码了吗？但实际上，被回滚的 PR 数量按相对比例反而在下降，稳定在 0.5% 左右。但我觉得这种交付节奏和 PR 数量真正有意思的地方在于，Grok Bot 的性能不仅保持稳定，而且在我们上线以来，在多个维度上都有所提升。启动、输入、打开新对话、切换对话，所有这些都变快了。

别忘了，Grok Bot 目前仍然是一个 Electron 应用。所以性能是有上限的，对吧？但它已经比市面上许多其他 AI 界面快得多了。对于一个有这种迭代速度、这么多贡献者的 Electron 应用来说，我觉得这已经相当不错了。

## 先修内层循环再建工厂

所以在动手搭建软件工厂、把所有能自动化的东西都自动化之前，每当你纠正你的智能体时，先试着通过改进代码库来做到这一点。先写一条 lint 规则，防止反模式再次出现，然后把这些旧模式也清理掉，再确保你的验证方案足够强。这项工作的大部分本来就是自动化的前提。如果你的内层编码循环产出的就是垃圾代码，那么把循环自动化只会产出更多垃圾代码，你得往问题上砸越来越多的 token，我们都知道那非常贵。

一旦你在代码库、静态分析、运行时和形式化验证上做了这些投入，你会发现很多事都变得可行，你可以很轻松地在这套基础上搭建自己的工厂。当你准备好时，Grok Bot 是构建那个循环的好办法。我们有大量连接器、可以启动 Cursor 云端智能体的例程，还有项目，让你能编排数百甚至数千个智能体。举个简单的例子，现在每次我们发布新版本，Grok Bot 都会先自动启动一个新的 Cursor 项目，对整个应用、整个构建做模糊测试。

它会像真实用户一样运行和使用应用来发现 bug，然后为发现的每个 bug 开一个修复 PR，并且自动合并——听起来很疯狂。那是因为我们的代码库足够好，PR 默认往往就是好的。我们合入的大部分产品代码已经不再真正需要深入的人工审查了。

所以当你有了扎实的基础和良好的有机架构，你就能把垃圾代码变成黄金，你就能以高质量、高速度交付，而不牺牲质量。我叫 poteto。Lauren，再次感谢你来听我的演讲。
