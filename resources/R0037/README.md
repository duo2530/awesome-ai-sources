## 一句话说明

一次关于“如何信任 Agent”的演讲：先把约束沉进代码与验证，再让 Agent 自己合并；作者自述团队上月 11,000 个 PR、revert 约 0.5%。

## AI 摘要与要点

演讲的主线是：提高 Agent 产出不靠更长的提示词，而靠把 Agent 的工作环境做得可信任。作者把环境分成三层，并用自己团队的仓库经验说明每一层怎么落地。

**三层环境（inverse pyramid，[2:03] 起）**

| 层 | 内容 | 作用 | 本库判断与注意点 |
|---|---|---|---|
| 确定性代码层 | API 设计、架构、重构、lint、类型系统、编译器、测试 | 直接约束 Agent 能做错什么，默认只允许正确写法 | 作者认为这是投入回报最高的一层；但需要先有架构判断力 |
| 验证层 | runtime verification、formal verification、property-based testing | 找 bug、检查不变量、确认 Agent 是否理解意图 | 作者明确说 formal verification “不是银弹”，只当另一层工具 |
| 少量散文 | rules、skills、AGENTS.md | 处理需要判断、无法机械化的部分 | 作者把散文放在最上层：能用代码约束的就不要只写规则 |

**代码库是花园（[3:27] 起）**

- 2024 年作者一天看三个同事的 PR，现在“更像 300 个”；每个工程师像带着几百上千个 Agent。
- 代码是 Agent 最大的输入；任何 workaround、反模式、弃用代码、技术债都会被下一个 Agent 当成“既有模式”复制。
- 因此要先把花园清干净，让 Agent 只复制好的东西。

**具体例子**

| 例子 | 做法 | 结果与代价 |
|---|---|---|
| Dune 里禁 useState 的 `useEffect` | 需要 nuance 才能用好的 API 容易产生 slop；在产品代码里直接禁，只在 Dune API 内部允许 | 这类问题被“分类消除”，不再需要在评审里抓；代价是失去部分灵活性 |
| Electron 主线程 / 渲染进程边界 | 用两个顶层目录与依赖图分析、lint 规则禁止跨层 import | 防止 Agent 把主线程代码 import 进渲染进程造成卡顿；规则简单但有效 |
| Markdown 逃生门 | Agent 会用文档、注释、rules 写下“为什么不按正确方式做”的理由，或把一次小纠正过度放大成硬规则 | 作者把这类行为当作需要警惕的信号 |
| Cursor 的命令式定时器 | Agent 用 `setTimeout` 等补 VS Code 命令式与 React 声明式之间的架构冲突，还写注释解释 | 定时器大量创建销毁导致 GC 与卡顿；根因是架构选择，不是 Agent 单个错误 |
| 禁 99% 注释 | 注释容易过期、不可强制，还给 Agent 不修根因的借口 | 改为用 lint 报错直接要求修根因；作者承认这是强主张 |
| 每次纠正变成确定性检查 | 要么加 lint / 类型 / 测试，要么用更好的 API 或架构消除问题 | 长期结果是“评审里要看的越来越少”，最终多数 PR 可自动合并 |

**验证怎么做（[9:40] 起）**

- 代码评审的重心从“逐行读 diff”变成“看验证产物”：视频、截图、图、formal verification 结果。
- runtime verification：给 Agent 运行代码的手段，例如 Chrome DevTools Protocol；配合 **feature map**（从用户视角列功能）与自定义 CLI，减少猜测、省 token、可测试。
- formal verification：用 TLA+ 对通知等跨设备流程做模型检查，用 Lean 证明自研虚拟化库没有闪烁/抖动；已经找到一些 bug，但仍在实验。
- property-based testing：用 Bombadil 对 UI 做属性测试，也抓到过 UI bug。
- 作者引述 Cindy 的推文：6 个月前她无法信任 Agent，因为总有隐蔽 bug 合入；缺的正是验证流程。现在她约 70% 的 token 花在验证上，作者说自己的用量也类似。
- 作者的判断：这些工具并不新，只是以前太贵、太难写和维护；Agent 把成本降下来了，所以“我们正进入软件测试与验证的黄金时代”。

**承诺之地（[13:22] 起）**

- 团队上月向生产提交 11,000 个 PR；客户端大约每天一个 stable 版本；10 月约 227 人至少贡献一个 PR。
- 作者称 revert 比例相对下降并稳定在约 0.5%，同时启动、输入、新开与切换会话等性能比发布时更好（仍是 Electron，作者承认有上限）。
- 收尾建议（[15:11] 起）：修 Agent 之前先修代码库；先用 lint 防新问题再清旧模式；把验证做扎实；内层循环如果产 slop，自动化只会放大 slop；基础打好后再建“软件工厂”；发布时自动 fuzz 整个应用、为每个 bug 开修复 PR 并自动合并——前提是代码库与门禁足够好。

## 适用边界与查漏补缺

- **单人演讲，公司内部数据**：3,000 / 11,000 PRs、0.5% revert、227 人、性能变化均为自述，没有原始报表、时间窗与统计口径；不能当行业基准。
- **强约束依赖团队水平**：禁 `useEffect`、禁 99% 注释、自动合并，都建立在作者团队有架构判断力与验证基础设施之上；低信任仓库照搬会放大风险。
- **转录质量有限**：专名混用（Grokbot / Graph Bot / Grabot / Growth Bot）与 “Potato” 等称呼来自语音识别；本库未核对画面与字幕，引用具体名称需回原视频。
- **form verification 仍在实验**：作者自己说“不是银弹”，未给 bug 数量、误报率或维护成本。
- **二手引用**：Cindy 的 70% token 是转述，未核验原推文。
- 未核验：视频画面、频道背景、`SpaceX SI` 的组织与作者职务、Dune / Grokbot 的代码、TLA+ 与 Lean 的模型。
