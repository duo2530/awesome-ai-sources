## 一句话说明

将 DDL、任务代码和业务文档先编译为带来源、结构契约与关系的知识页面，再通过域索引、关键词和图遍历支持问答与影响分析。

## AI 摘要与要点

文章将知识质量与检索质量分开处理：检索前先治理材料的分散、冲突和腐化；查询时再选择合适路径召回。LLM 负责语义生成与判断，脚本负责抓取、结构校验、图构建和对账，主观归属与聚类由人确认。

| 环节 | 文中设计 | 值得参考的地方 |
|---|---|---|
| 原材料入口 | 清单抓取后按 ready、pending、archive 分流，生成只消费 ready | 缺失材料先治理，不把不完整内容直接包装成知识 |
| 页面生成 | Schema 约定 YAML frontmatter 与 Markdown 正文，sources 记录出处 | 关系与元数据可解析，描述与来源可追溯 |
| 生成和判断分开 | 基础页只写有材料支撑的内容，需推断字段先留空；再提候选交人确认 | 避免生成时将主观判断固化成事实 |
| 基础与聚合分开 | 表、接口、数据集、概念为基础页；域、看板、指标和索引再聚合 | 避免生成器重复解释相同来源，依赖就绪后再汇聚 |
| 显式关系 | 从 frontmatter 和 Wikilink 构建 graph.json，正向边为主，反查并回填下游 | 关系遍历补关键词没有命中的关联对象 |
| 页面和全局验证 | 校验字段与 DDL，再做数量、Schema、链接、域格式、语法和图完整性检查 | 单页一致性与全局结构分别检查，失败不发布 |
| 检索路由 | 精确查询读实体，关系查询走图，模糊查询做域与关键词召回、图扩展和精排 | 不把所有查询都交给同一种检索手段 |
| 保鲜 | 按材料、页面和 sources 对账局部重生成，图重建与健康检查收尾 | 将增量处理与整体一致性检查结合 |

### Wiki 与 RAG 的关系

文章把 Wiki 定位为构建期的知识加工产物，把 RAG 定位为查询期的召回手段。高质量页面可以作为检索语料；日志、监控、实时表数据等时效性事实按需通过工具获取，不固化进静态 Wiki。开篇对直接套 RAG 的批评，针对的是未治理的原材料，不能概括为不用 RAG。

### 检索怎样避免只看标题

模糊查询先推断相关域，域与关键词并行召回候选，再沿图扩展；脚本粗排后，LLM 必须逐张读候选详情。覆盖需求是硬条件，覆盖合格后再按查询意图权衡相关性与通用性。文中 2—3 个域、4—6 张候选是其场景参数，本库没有验证最优值。

## 适用边界与查漏补缺

- SQL 生成、耗时提升和遗漏率 20%→0% 等是文章场景自述，未提供本库可重放的样本和评测数据；不作为普遍准确率或零遗漏保证。
- 代码可作为当前行为的依据，但须确认版本、部署与环境；代码也可能有 bug，不能据此覆盖产品意图、契约或业务口径的争议。
- sources 路径可追溯不等于证据永久可重现：仍需版本或内容标识、来源时间、删除处理与生成依据。单看路径相同不能检测同路径内容变化。
- Schema、字段和数量对账能发现结构缺陷，不能独立证明口径、聚类、血缘语义和答案正确；文中语义审查与人工确认仍重要。
- 只存正向边减少双向维护，但 graph.json、downstream 回填与聚合页仍是派生产物；一致性不会自动消失，需明确构建顺序、失效规则与发布快照。
- 健康检查将 graph.json 与 frontmatter 一并描述为 YAML 语法检查；实际实现仍应按各格式及 Schema 验证。DDL、所有类型页面与图节点不能简单要求总数相等，需按对象类型核对范围。
- 先限定少数域和固定候选数可能漏召回，入度高也不等于正确或适合；应以代表性查询、召回遗漏与新鲜度证据验证。
- 九章明确任务/看板清单正式落地、自动源材料变更触发、向量检索与 benchmark 仍在规划；前文流程描述不代表这些能力已全部完成或持续运行。
- 权限继承、数据脱敏、可见性过滤、恶意材料与 Prompt 注入、生成发布原子性及并发冲突仍缺充分实现说明。
- 本篇来自数据仓库场景。本库的来源、正文、摘要、标签和问题索引可参考其职责分离，但本轮没有引入图数据库、额外 JSON 名单、检索服务或改造目录结构。
- 未运行原文技能、调用业务系统、生成或执行 SQL、配置定时任务；用户阅读与实践状态仍未记录。
