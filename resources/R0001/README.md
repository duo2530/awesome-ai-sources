## 一句话说明

把 Agent 的失败从“模型不够聪明”重新归因为“环境没造好”，用四条铁律、六种工程模式和一个钉钉招聘案例，说明 Harness 该怎么搭、约束该放在哪。

## AI 摘要与要点

文章是工程实践复盘，不是可运行的框架文档；观点密度集中在第四至第八节。

| 环节 | 作者的主张 | 本库判断与注意点 |
|---|---|---|
| 问题归因 | Agent 的失败不是模型的问题，而是环境设计的债；Harness Engineering 的定义是“每发现一次错误，就工程化一个让它不再犯的解” | 把注意力从换模型转向改环境，方向与 R0022、R0021 一致；“所有失败都是环境债”是强归因，忽略了模型能力上限与任务本身的不确定性 |
| 核心公式 | Agent = Model + Harness；LangChain 仅优化 Harness 就在 Terminal Bench 2.0 从第 30 升到第 5、52.8 → 66.5 分 | 数字转引自 [2] LangChain 官方博客；本库未打开原文核对，也未复现该实验 |
| 三代范式 | Prompt → Context → Harness Engineering，形象对比为“对马喊话 → 给马看地图 → 造高速公路” | 是作者的演进叙事，不是行业分期标准；三代可以并存，后一代不取消前一代的具体技巧 |
| 四条铁律 | 上下文越少越好；专才 Agent 赢通才；状态写文件不塞上下文；能写成 Linter 的别写文档 | 可执行、可检查，是本篇最有复用价值的部分；与 R0022 的 AGENTS.md 目录化、自定义 lint 互相印证；第一条的“阈值”作者主动不给具体百分比 |
| 六种模式 | 双阶段 Init+Exec、工具签名即文档、Sub-Agent 隔离、上下游反压、Agent 审 Agent、熵管理与文档园丁 | 工程套路汇编；模式 1 称来自 Anthropic 实践但未给官方链接；照抄前需按本团队反馈回路成熟度裁剪 |
| 招聘案例 | 第一版全能 Agent（600+ 行 Prompt；工具数原文一处写 13 个、配图写 38 个）失败；改为 2 Agent + N Skill + Workspace 状态文件 + Linter 护栏后达上线门槛 | 团队内部实测自述，无样本量、无对照设计、无原始报表；相对结论可作方向参考，不能当行业基准数字 |
| 三条经验 | Agent 数量不超过 3 个、Skill 可以无限加；RPA 接缝处做事务边界；对外说话的 Agent 必须接硬护栏 | 与铁律二至四一一对应；其中“Agent 数量也是上下文成本”是对“多 Agent 分工”常见建议的反向提醒 |
| 趋势判断 | Prompt 工程师让位于 Agent/Harness 工程师；A2A 标准化；Agent 即新的操作系统；模型与 Harness 接口标准化 | 作者自附可证伪条件，态度可取；但条件未给测量口径，仍属判断而非预测 |
