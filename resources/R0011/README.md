## 一句话说明

当 AI 接过编码，人应集中于定义问题和验收判据；把重复错误交给框架、运行时与独立执行证据，并检验评测和事实采集机制自身是否可靠。

## AI 摘要与要点

文章围绕特殊技术栈与长期业务系统展开，同时用通用栈的新平台作对照。作者的核心判断是：产出变多并不会同步提高人的审查能力，必须把“听 AI 说做完”转成可复查的执行事实，再把人的注意力集中到取舍与验收条件。

| 部分 | 主要思路 | 值得回看的案例 |
|---|---|---|
| 框架与工具 | 不无限堆提示词，将可重复错误沉入环境；硬门禁需有准确判据 | 声明式 mock 自动还原、超时返回分析包；误报告警反而会带偏 |
| 编排与 runtime | 审视上下文、工具参数、恢复与限额是否可观察、可干预 | 完整 Team 流程过脆，收窄测试流程后仍有常驻 reviewer 的偏向问题 |
| 评测 | 先定义题集与可执行判据，再决定是否需要重平台 | 文件归属被误当成召回能力；变异测试还需验证等价变异和参照测试 |
| 人的职责 | 保留目标、边界、什么算缺陷和验收取舍的判断 | 不只审实现，还要审 AI 写出的测试和事实采集链 |
| 嵌套闭环 | 候选、独立验证、人审、入库与反馈分别留痕 | 平台重跑用例、失败有明确状态、区分采集失败与未覆盖 |

评测部分可进一步提炼为三条阅读重点：

- **测试通过不等于有查错能力**：作者使用变异击杀率检验断言，并在入题前处理等价变异和参照测试错误。
- **结果要对应所问的问题**：评分器若在量文件布局或格式，就不能把分数解释成测试能力；没有裸模型基线时，也不能证明插件增益。
- **评测同样会被污染**：据存活变异改 skill 后再用同一批题评估，会高估改进；重复跑数、留出数据与用途说明都很重要。

作者还区分临时对齐用的 spec 与长期维护的设计说明，并承认部分平台能力仍在建设。这里呈现的是经验和取舍，不是通用于所有项目的实施标准。
